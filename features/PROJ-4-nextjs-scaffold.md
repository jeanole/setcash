# PROJ-4: Next.js App Scaffold + PostgreSQL + Docker

## Status: Planned
**Created:** 2026-03-01
**Last Updated:** 2026-03-01

## Context
Parallel rewrite of vBudget using Next.js 14 (App Router), Prisma ORM, and PostgreSQL.
The new app lives in `/nextjs/` inside the existing repo. The existing Express app remains
untouched during the migration. All migration work happens on branch `to_nextjs`.

## Dependencies
- None (this is the foundation step)

## User Stories
- As a developer, I want a working Next.js 14 App Router scaffold so that I can build
  the new app incrementally without touching the existing Express app.
- As a developer, I want a Prisma schema that mirrors the current SQLite schema so that
  the data model is established before any feature pages are built.
- As a developer, I want a `docker-compose.test.yml` so that I can spin up the new Next.js
  app + PostgreSQL locally and test end-to-end without affecting the production Express app.
- As a developer, I want a basic shared layout (header, sidebar shell, main content area)
  so that subsequent feature pages have a consistent frame to drop into.

## Acceptance Criteria
- [ ] `/nextjs/` directory contains a Next.js 14+ project initialised with App Router (`app/` dir)
- [ ] TypeScript is configured (`tsconfig.json` present, strict mode on)
- [ ] Prisma is installed and configured to connect to PostgreSQL via `DATABASE_URL` env var
- [ ] Prisma schema (`schema.prisma`) defines all models matching the current vBudget tables:
      `User`, `Project`, `ProjectMember`, `Bill`, `BillImage`, `BillMotive`, `BillCategory`,
      `Category`, `Motive`, `Vgeld`, `EditLog`, `Settings`
- [ ] `prisma migrate dev` runs successfully against a fresh PostgreSQL instance
- [ ] `docker-compose.test.yml` at repo root starts: `nextjs` service (port 3001) + `postgres` service
- [ ] `.env.test` (gitignored) documents all required env vars with placeholder values;
      `.env.test.example` is committed with the same keys and dummy values
- [ ] `npm run dev` inside `/nextjs/` starts without errors on port 3001
- [ ] Root layout (`app/layout.tsx`) renders a sidebar shell and main content slot
- [ ] A placeholder home page (`app/page.tsx`) renders "vBudget — Next.js migration in progress"
- [ ] Branch `to_nextjs` is the only branch where `/nextjs/` changes are committed

## Edge Cases
- The existing Express app must not be modified in any way during this step
- `docker-compose.test.yml` must not conflict with the existing `docker-compose.yml` (different
  service names, different host ports)
- If `DATABASE_URL` is missing, the Next.js app must fail fast with a clear error, not silently
- Prisma schema must use `uuid` as default ID strategy (not auto-increment integers) to avoid
  collision with future data migration from SQLite integer IDs — use `String @id @default(uuid())`
  but also store the legacy SQLite integer id as `legacyId Int?` for migration mapping

- Database: PostgreSQL 15+
- Language: TypeScript (strict)
- Node: 20+
- Port: 3001 (Next.js dev / docker), 5432 (Postgres internal)
- Branch: `to_nextjs`

### B) Data Model (19 Prisma Models)

All models use a **UUID string** as their primary key. Every model also carries a
`legacyId` integer field (nullable) to store the original SQLite integer ID. This field
is essential for the data migration script in PROJ-6 to resolve foreign-key references.

Timestamps that are stored as plain text in SQLite become proper `DateTime` fields in
PostgreSQL. Boolean flags (stored as 0/1 integers in SQLite) become `Boolean` fields.
JSON blobs (`ocr_fields`, `changes`) become `Json` fields.

**Auth**
```
User
  id           UUID (primary key)
  legacyId     Int? (SQLite id for migration)
  email        String (unique)
  passwordHash String
  isSuperAdmin Boolean
  defaultProjectId UUID? → Project
  createdAt    DateTime
```

**Multi-tenancy**
```
Project
  id        UUID
  legacyId  Int?
  name      String
  subtitle  String?
  createdAt DateTime

ProjectMember
  id          UUID
  project     → Project
  user        → User (by email)
  role        Enum: user | admin
  position    → ProjectPosition?

ProjectPosition
  id        UUID
  project   → Project
  name      String

ProjectSettings
  projectId  UUID → Project
  key        String
  value      String?
  (composite primary key: projectId + key)
```

**Expense Tracking (core)**
```
Bill
  id              UUID

  submittedByEmail String → User
  date            DateTime
  billNumber      String?
  type            String?
  vendor          String?
  item            String?
  comment         String?
  motiveLegacy    String?   (kept for historical display only)
  brutto19        Decimal
  brutto7         Decimal
  brutto0         Decimal

  grossAmount     Decimal
  status          Enum: confirmed | pending | approved | rejected | paid
  ocrStatus       Enum: null | pending | done | failed
  ocrFields       Json?     (per-field AI extraction results + verification state)
  telegramCaption String?
  filename        String?   (legacy single-file field)
  createdAt       DateTime

BillImage
  id        UUID
  bill      → Bill (cascade delete)
  filename  String?

  id         UUID

BillCategory
  id         UUID
  bill       → Bill (cascade delete)
```

```
  id        UUID
```

### C) Docker Test Stack (`docker-compose.test.yml`)

Two services, completely isolated from the production compose:

```
vbudget-next   — Next.js app
  build:  ./nextjs/Dockerfile
  port:   3001 (host) → 3001 (container)
  env:    DATABASE_URL, NEXTAUTH_SECRET, NEXTAUTH_URL, GOOGLE_* etc.

postgres-test  — PostgreSQL 15
  image:  postgres:15-alpine
  port:   5433 (host) → 5432 (container)   ← different host port from any local PG
  volume: vbudget-pg-test-data (named volume)
  env:    POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
```

Service names (`vbudget-next`, `postgres-test`) and host port (3001, 5433) are
deliberately different from any production values to prevent accidents.

### E) Tech Decisions (Why)

**Next.js App Router over Pages Router**
The App Router allows React Server Components — components that fetch data on the server
and send plain HTML to the browser. This means the bill list, budget matrix, and reports
pages will load fast with no client-side fetch waterfalls.

**Prisma over raw SQL or Drizzle**
Prisma auto-generates TypeScript types from the schema, so every query is type-safe.
It also handles complex migration management (`migrate dev`, `migrate deploy`) cleanly.
The trade-off is slightly slower query speed vs. raw SQL, which is acceptable at vBudget's
scale.

**PostgreSQL over keeping SQLite**
SQLite works for a single-server, single-writer setup, but PostgreSQL handles concurrent
admin actions, proper JSON querying, and UUID generation natively. It also allows the app
to scale to a cloud DB later without schema changes.

**UUID primary keys with `legacyId` fallback**
SQLite uses auto-increment integers; PostgreSQL can use sequences too, but UUIDs are
safer when IDs appear in URLs (no enumeration attack). The `legacyId` field lets the
migration script translate old integer foreign keys before the new UUID relationships
are fully built.

**Separate `docker-compose.test.yml`**
A separate file guarantees developers can never accidentally `docker-compose up` the
test stack against the production volume. The different service names also mean the
two stacks can run side-by-side on the same machine.

### Bugs Found

#### BUG-1: `prisma/migrations/` directory missing and gitignored [Architecture] [Deploy]
- **Severity:** High
- **Steps to Reproduce:**
  1. Clone the repo on branch `to_nextjs`
  2. Run `ls nextjs/prisma/migrations/`
  3. Expected: Migration files present (commit message says "initial database migration")
  4. Actual: Directory does not exist

- **Impact:** Developers cannot run `prisma migrate deploy` to set up a new database from the repo. They must run `prisma migrate dev` interactively, which is not suitable for CI/CD or production deployments. Prisma's official guidance is to commit migration files.
- **Priority:** Fix before deployment
