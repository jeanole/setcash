## Phase Classification: Backend-Only

Phase 1 has **no frontend deliverables**. All six requirements (SEC-01, SEC-02, SEC-03, SEC-04, QUAL-04, QUAL-05) are server-side changes:

- Path traversal guards on API routes (server-side validation)
- DB role re-fetch in API route handlers (server-side authorization)
- Origin header validation in Edge middleware (server-side CSRF defense)
- next-auth version pinning (package.json)
- @types/* dependency reorganization (package.json)
- better-sqlite3 removal (package.json)

No new pages, components, styles, or visual changes are introduced in this phase.

## Copywriting Contract

The only user-facing text change is the API error response when a demoted user attempts an admin action (SEC-02, decision D-04):

| Element | Copy |
|---------|------|
| Role demotion API response | `{ "error": "Session expired - role changed", "code": "ROLE_CHANGED" }` |
| Cross-origin rejection API response | `{ "error": "Cross-origin request rejected" }` |
| Invalid origin API response | `{ "error": "Invalid Origin header" }` |
| Path traversal rejection API response | `{ "error": "Path traversal attempt blocked" }` (caught by route try/catch, returned as 400) |

These are JSON API responses, not rendered UI copy. The existing client-side error handling (`fetchWithError` and hook error states) will display these via the existing toast/error patterns without any frontend changes.

**Client-side behavior on 401 with `ROLE_CHANGED`:** The existing `fetchWithError` throws on non-OK responses. Hooks catch errors and set error state. A 401 response should trigger a page reload or redirect to login. If the existing client does not handle 401 globally, a minimal global 401 handler may be needed -- but this is a Phase 1 implementation detail, not a design contract item. No new UI is required; the browser redirects to the existing login page.
